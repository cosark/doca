# PostgreSQL 插件初始化权限验证

日期：2026-10-16。代码基线为宿主 0.1.29，含当前工作区改动。使用临时 PostgreSQL 17/18 容器、随机独立测试库与账号、临时文件存储；未连接部署数据库。

## 已发布宿主的故障

原有 PostgreSQL 插件测试让插件账号拥有整个业务库，未覆盖由管理员拥有数据库、仅授权受限账号使用的部署。

按原文档只授予受限账号业务库 `CONNECT, CREATE`，首次 `defineSchema` 在创建 `public._doca_shared_plugin_database` 时产生 SQLSTATE `42501`：`permission denied for schema public`。存储边界将此异常包装为 `Plugin storage operation failed`，丢失配置诊断。独立普通主库账号、插件库所有者账号组合则能正常安装和读写。

## 改动范围

- 项目所有者明确要求账号权限由部署者管理。移除超级用户、`CREATEDB`／`CREATEROLE`／`BYPASSRLS`、角色成员关系及核心表访问权限的拒绝检查；接受主库与业务库使用同一登录账号，仍检查业务库目标与核心库分离。
- 缺少插件库 URL、缺少业务库 `CREATE` 或首次共享标记初始化所需的 `public` 权限时，返回固定的配置诊断。应用不自动修改账号权限。
- 原始驱动错误、SQL 内容和业务回调异常继续隐藏；只透传宿主明确生成的配置诊断。
- 中英文部署文档和环境配置示例改为账号及权限由部署者选择，专用账号作为可选示例；补齐业务库及 schema 级授权命令，并说明回退至旧宿主会重新启用旧账号检查。
- 核心 DDL、共享标记位置、存储格式 3、SDK 和数据版本规则没有改变。现有格式 2 活跃安装的拒绝，以及已清理历史命名空间的处理路径未修改；没有旧数据转换或迁移。

## 验证结果

- PostgreSQL 17/18：安装管理、共享库、托管存储、凭证及账号／授权测试，各 58 项全部通过。
- SQLite：上述测试中 54 项通过，4 项 PostgreSQL 专用测试跳过。
- 账号回归：逐项接受超级用户、`CREATEDB`、`CREATEROLE`、`BYPASSRLS`、角色成员关系及核心表显式授权；每次建立新连接验证，同一核心数据库目标仍被拒绝。另验证主库与业务库使用同一管理员账号，业务记录重启后保留。
- 普通账号回归：缺少 URL、只有数据库权限、同时缺少 `public` 的 `USAGE`、缺少数据库 `CREATE`、授权后重试、失败时核心声明与目标插件 schema 保持原状、已有共享标记不要求重新授予 `public CREATE`、重启后记录保留。
- PostgreSQL 18 实际插件验证：在两个独立数据库使用同一个 `postgres` 超级管理员账号，通过管理员 HTTP 上传真实 `@smartdoca/doca-resources-manage@0.1.4` 编译发行文件，重启后成功创建全部 20 张业务表；登录后通过 `/preferences` 写入设置，再次重启读回。验证前后该账号均为超级用户，全程不修改角色或授权，不修改插件源码或插件持久化结构。
- 用不含真实凭据的同结构环境配置检查当前 Docker Compose：插件库 URL 能从 `.env` 转发到服务；未配置的插件 SQLite 路径／旧设置为待省略的空值；容器监听地址由 Compose 设为 `0.0.0.0`。
- `pnpm typecheck`、`pnpm docs:check`、变更文件格式检查和 `git diff --check` 通过。

用户先后提供的查询截图确认：旧宿主因 `rolsuper = true` 拒绝插件账号；降权后，容器内新连接看到角色属性均为 `false`、数据库 `CREATE` 和 `public USAGE` 为 `true`，但 `public CREATE` 为 `false`。这确认了两个先后出现的阻断因素。用户随后明确要求取消程序强制的账号权限限制，当前实现及上面的最终验证遵循该决定。数据库实际权限不足仍由 PostgreSQL 拒绝，应用提供明确诊断。未保存或复用所提供的生产凭据，未发布镜像或修改部署配置。
