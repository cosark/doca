# 插件独立业务库

[English](plugin-database-isolation.md)

2026-10-14 工作区实现，尚未发布或部署到生产。用户已确认通过正常卸载丢弃旧插件业务数据，不做迁移。实际发行版升级验证以 0.1.24 镜像为来源；更早的宿主兼容代际限制仍有效。

## 归属与配置

每个插件的业务库仍由宿主管理。插件继续使用现有 `storage.sql.v1`、version 1 结构声明和 `dataVersion`，不取得连接串、驱动或磁盘路径。业务表采用声明中的逻辑名称；`_doca_plugin_store` 绑定准确的插件 ID、安装代次、数据版本及规范化结构。

核心库保留用户、文档、权限、安全审计、原始 AI 用量、插件注册和归档索引、安装命名空间、加密凭证、私有对象引用及对象回收意图。文件和凭证服务保持既有归属与权限。核心目标 DDL 和 `schema_baseline.id` 不变。

SQLite 每插件一个文件，默认目录为 `<核心数据库路径>.plugins/`，可用 `DOCA_PLUGIN_DATABASE_DIR` 覆盖。文件名采用插件 ID 的 SHA256，权限为 0600，内部业务表名可读。目录必须放在持久化本地卷并纳入备份。SQLite 适用于单宿主，不能通过网络文件系统实现共享部署。内存数据库嵌入场景使用各自独立的插件内存库。

PostgreSQL 由运维预先创建每插件独立数据库和受限登录角色。宿主不使用核心账号自动建库、建角色，也不回退到核心库。启用使用 SQL 的插件前配置：

```dotenv
DOCA_PLUGIN_DATABASES_JSON='{"version":1,"databases":{"example.mail":{"url":"postgresql://doca_mail:replace-me@postgres:5432/doca_mail","poolMax":2}}}'
```

每项显式配置连接池上限。按插件池、核心/AI/webhook 池之和乘实例数量计算连接预算。拒绝重复目标、核心数据库、高权限角色、角色成员资格及核心表访问权限。各角色只授权自己的业务库，额外撤销不需要的 PUBLIC 连接与 schema 权限。共享端点下会核对实际数据库身份和核心表权限。插件不取得连接配置及密钥。进程/容器隔离不在本次范围，插件仍在受信任宿主进程内执行。

变更 URL 或目录不等于迁移。安装已有结构记录时，配置到空替代库会被拒绝；应保留原配置，或显式卸载重装。

## 安装、结构声明与卸载

新安装使用宿主存储格式 2，初始声明为 `storageVersion: 2`、`schema: null`。旧格式的有效安装一律拒绝，包括 definition 为 null 的无状态插件。核心结构核对会在持久化结构变更前报告残留 `plugin_<56位十六进制>` 旧业务表。没有旧格式读取、自动删表、结构转换或双写。已由旧版卸载的命名空间历史记录保留，显式重装时增加代次并记录新声明。

首次声明先锁定核心命名空间，在一个业务事务内创建业务表和安装标记，再在核心事务内记录准确结构。若业务创建已提交而核心记录未提交，重试只接受完全相同的规范化标记、代次及结构，并核对实际表结构；不能接纳旧安装或其他数据库。缺表、丢失数据库文件、类型/默认值/可空性/主键/唯一约束变化和额外表会报错，不会静默重建。用户事务回调只执行一次，结束后句柄失效；业务提交后核心提交失败属于结果不确定，须通过业务幂等记录和回读确认，不能自动重放回调。

业务事务持有核心命名空间锁直至业务提交结束，卸载不能在已准入写入尚未提交时使代次失效。先执行业务 uninstall 钩子；成功后，核心注册事务将命名空间标记为 removed、清除安装选择和凭证，并登记私有对象回收。用户文件、权限、回执和发行包保留。钩子失败保留安装；钩子产生的外部副作用不能回滚。

业务表在核心提交后清理，保留的命名空间声明就是持久化清理意图。启动、定时任务、卸载和安装尝试会重试。清理先锁定并核对 removed 代次，验证业务标记，仅删除声明中的业务表和标记。遇到额外表或标记不符会失败，不产生部分删除。业务清理已提交而核心意图尚未清除的中断可安全重试；首次声明中断也能通过准确业务标记清理。重装等待清理完成、增加代次，再创建空结构；旧句柄不能访问新代次。没有跨库原子提交或自动集群任务排空，全部实例仍须重启。

## 已确认的升级与恢复

1. 备份原核心库、文件存储及部署配置，包括凭证主密钥。
2. 在旧宿主仍运行时正常卸载全部外部业务插件。此操作明确删除插件私有业务记录、加密凭证和私有对象；账号绑定和插件配置需重建。不要先手动删表再卸载。
3. 停止全部宿主实例，按需预建并配置 PostgreSQL 插件库。部署本实现，继续使用既有核心库、普通用户文件和主密钥。
4. 重装插件并重启全部实例。业务模型在独立空库中重新建立，不导入旧业务数据。

第二步失败时继续使用旧宿主，先处理卸载错误。新版启动拒绝残留安装或旧表时，返回旧版完成卸载，不能重置核心库。新版尚未产生写入时，恢复卸载前状态需要对应的原数据库/文件备份和旧部署；已撤销的外部授权可能仍须重新绑定。新版写入后直接回退代码或恢复旧备份会丢失后续数据，须保留新库并另行确认恢复方案。旧宿主不能读取新插件库布局。

## 验证

隔离 SQLite 与 PostgreSQL 17/18 测试覆盖物理隔离、受限角色、重复初始化、独立连接、回调回滚、旧代次失效、存储丢失、拒绝旧表时保留核心数据、初始化中断和卸载清理重试。实际 0.1.24 镜像创建需保留的核心记录及旧插件行，正常卸载后，由工作区代码打开同一核心库并在独立空业务库中重装。执行脚本为 `scripts/verify-plugin-database-isolation-upgrade.ts`，验证记录见待发布说明。以上不代表生产部署或支持新旧版本混跑。
